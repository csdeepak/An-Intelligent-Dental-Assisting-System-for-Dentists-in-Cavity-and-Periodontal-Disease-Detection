WHY THIS IS THE PIPELINE DEFAULT — AND WHY THAT IS NOT THE SAME AS "IT PASSED"
------------------------------------------------------------------------------
`docs/research/T0.6_detector_reconciliation.md` §2 pre-registered, before any seg run
existed, that the segmentation model replaces the frozen bbox model as canonical Stage-1
ONLY IF, on the held-out test split, BOTH of:

    Box  mAP@0.5 >= 0.75      -> 0.8100   PASS
    Mask mAP@0.5 >= 0.65      -> 0.6383   FAIL  (short by 0.0117)

**The mask bar was missed and the bar was NOT changed.** §2 stands exactly as written; this
model does not satisfy it. Adoption is a SEPARATE, DATED HUMAN DECISION taken on 27 Aug 2026
on the strength of the box result alone (+2.76 points over the superseded detector, 0.8100 vs
0.7824, same frozen split, otherwise identical config). Recorded as such rather than presented
as the bar having been met, because those are different claims and only one of them is true.

What follows from adopting a model that missed the mask bar:
  - **The masks are NOT validated to the standard §2 asked for.** This model is used for its
    BOXES ONLY, exactly like its predecessor. **R2 (mask-aware cropping) stays UNWIRED** — it
    was the thing the 0.65 floor existed to protect, and nothing has changed that judgement.
  - Any future use of this model's masks needs its own pre-registered evaluation first.
  - The superseded bbox detector is retained unchanged and hash-pinned at
    `models/06_yolo_detection_a100_run/` — every number published before 27 Aug was measured
    on it, so it must stay byte-reproducible.

⚠️ **DOWNSTREAM NUMBERS MEASURED ON THE OLD DETECTOR ARE NOW STALE.** Stage-1 recall (67.0%)
and Stage-2 FDI end-to-end (46.5/46.6%) were measured on DENTEX against the bbox detector and
have NOT been re-measured. DENTEX is not present on the machine where the swap was made, so
this could not be done at adoption time. `run_inference.py` now emits these as `None` with an
explicit "pending re-measurement" note rather than printing figures that would misdescribe the
running pipeline. **Re-measure on a machine that has DENTEX before quoting any end-to-end
number.**

    bbox detector (canonical)   test mAP@0.5 = 0.7824

Training with instance masks produced a BETTER box detector than training on boxes alone,
on the same frozen split with an otherwise identical config. That is a real, reportable
result and is directionally consistent with DentFound's ablation (masks improve detection).
It is also the number that matters for the Stage-2 ceiling, since Stage-2 end-to-end is
capped by detector recall, not by mask quality.

CAVEAT, pre-registered in T0.6 §2 and repeated here rather than buried: the seg test ground
truth holds 3,930 instances vs the bbox test set's 3,924 — 6 real teeth (0.15%) that the bbox
converter dropped on a corrupt `bounding box` field and this converter keeps. Same images,
same split. Near-like-for-like, not exactly like-for-like.

DATA CORRECTION — this run's inputs differ from the first, withdrawn attempt
----------------------------------------------------------------------------
An earlier 90-epoch run on this same config was WITHDRAWN: every instance mask in its
training data was spatially misaligned with its image. Two independent defects, both fixed
before this run (RESULTS_LOG.md 2026-08-27a):

  1. teeth_polygon.json stores points as [y, x]; teeth_bbox.json uses [x1,y1,x2,y2].
     The converter had inherited the bbox converter's "no transform" assumption.
  2. This machine's Radiographs_rotated/ predates the 22 Aug rotation-direction fix and
     was 180 degrees out.

Verified before training, against teeth_bbox.json (the ground truth the canonical bbox
detector was trained on), over 3,225 train instances:

     broken dataset   median IoU 0.000    1.6% agreement at IoU>=0.5
     dataset_seg_v2   median IoU 0.837   99.4% agreement at IoU>=0.5

The same gate was re-run ON THE GPU MACHINE immediately before launch and passed identically,
so the data actually trained on is verified, not merely the data that left this laptop.

WHAT WOULD CLOSE THE MASK GAP (not attempted — would need a new pre-registration)
---------------------------------------------------------------------------------
Mask mAP@0.5 0.6383 vs a 0.65 bar is a 1.2-point miss, close enough that ordinary run-to-run
variance is a plausible part of it. Anything done to chase it must be pre-registered BEFORE
running, exactly as §2 was, or the result is not honest:
  - the 0.65 floor was itself a judgment call ("a mask must at minimum give a materially
    usable instance signal for R2"), not derived from a prior measurement
  - mask quality is bounded by the polygon ground truth, which uses the largest-fragment-
    per-object heuristic; multi-fragment teeth lose their smaller fragments
  - `mask_ratio` (4) and `overlap_mask` (True) were inherited as Ultralytics defaults and
    were never tuned for this data
