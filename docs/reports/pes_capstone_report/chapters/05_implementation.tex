\section{Technology Stack}
\label{sec:impl-stack}

The current implementation is split across reusable Python modules under
\texttt{src/}, command-line placeholders under \texttt{scripts/},
notebook-based model development under \texttt{notebooks/}, and saved model
summaries under \texttt{models/}.

PyTorch and torchvision are used for the classification models, OpenCV and
NumPy are used for crop extraction and mask processing, Pandas is used for
annotation joins, and scikit-learn is used for evaluation metrics. The
periodontal engineering work in this repository is code backed: the parsing,
crop generation, overlap computation, and tooth-number conversion helpers all
exist as standalone source files and have accompanying tests. The caries branch
is currently notebook backed through the collaborator's DENTEX experiments.

\section{Module 1: \textit{Caries Cascade Classifier}}
\label{sec:impl-module1}

The collaborator's caries notebook implements a two-stage cascade rather than a
single three-class model. In the first stage, a ResNet18 classifier predicts
caries versus no-caries from tight tooth crops. The notebook resizes every crop
to \(224 \times 224\), applies ImageNet normalization, replaces the ResNet18
fully connected layer with a two-class head, and trains using weighted
cross-entropy and Adam optimization. Best-checkpoint selection is done by
validation accuracy.

The second stage reuses the same backbone family but changes the task to
caries versus deep caries. The collaborator's notes describe the intended
transfer-learning logic clearly: reuse the phase-1 representation, reset the
final classifier, and fine-tune at lower learning rate so the model adapts to
severity cues rather than relearning generic tooth appearance from scratch. The
checked notebook contains multiple phase-2 refinement runs, ending with a final
improved validation result after adjusting the class weights and continuing
low-learning-rate fine-tuning.

From an implementation-quality perspective, the strongest part of the caries
work is the architectural decomposition into a coarse-to-fine cascade. The
weakest part is experiment tracking. The exported notebook preserves the phase-2
reports, but not the final printed phase-1 classification report. It also
defines a training augmentation block for the severity stage without actually
using that transform in the final data loader. These issues do not invalidate
the model development, but they must be documented because they affect how
confidently the reported metrics can be reproduced.

\section{Module 2: \textit{Dataset Exploration and Annotation Parsing}}
\label{sec:impl-module2}

This module is implemented in \texttt{src/data\_loader.py} and the accompanying
exploration notes under \texttt{docs/exploration/README.md}. The key purpose of this
module is to convert the raw Tufts annotations into a form suitable for
tooth-level periodontal analysis. Three specific preprocessing bugs were
critical. First, the expert and bounding-box JSON files are lists of records,
not dictionaries keyed by image name; the correct join key is the stem of the
\texttt{External ID} field. Second, the raw tooth boxes are stored as
\([y_1, x_1, y_2, x_2]\), not \([x, y, w, h]\). Third, the expert mask values
encode lesion instances rather than severity classes, which invalidated an
earlier segmentation-based severity plan.

The parsing implementation therefore performs three concrete operations:
\begin{enumerate}
  \item load expert descriptions and derive image stems from \texttt{External ID};
  \item load tooth boxes and convert them to \([x, y, w, h]\);
  \item classify expert masks as empty versus annotated and then join all
  sources on image stem.
\end{enumerate}
This module is foundational because every downstream periodontal experiment
depends on the correctness of these joins and coordinate conversions.

\section{Module 3: \textit{Bone Loss Dataset Construction}}
\label{sec:impl-module3}

The dataset-construction logic is implemented primarily in
\texttt{src/crop\_generator.py} and \texttt{src/label\_assigner.py}. Starting from a valid
tooth bounding box, the system constructs an expanded crop that includes the
root and surrounding bone. A randomized jitter option is also available to
simulate detector localization noise. After crop extraction, the corresponding
expert mask is cropped to the same region and the overlap ratio is computed.
This overlap ratio directly drives the bone-loss label assignment.

This implementation choice is important because it converts sparse expert mask
annotations into a tooth-wise supervision signal without requiring full lesion
segmentation at inference. It also provides a mathematically simple and
reproducible bridge between the region annotations supplied by Tufts and the
tooth-centric output required by the final system design.

One limitation of the current resampling implementation is redundancy within
the diseased class. The diseased pool already contains jittered near-duplicates
of the same teeth, and the offline augmentation procedure further multiplies
them. This has been retained in the current report because it reflects the
actual implementation, but it should be improved in a later iteration through
deduplication or per-image contribution limits.

\section{Module 4: \textit{Bone Loss Binary Classifier Training}}
\label{sec:impl-module4}

The binary periodontal classifier is the most mature module in the repository.
It uses a ResNet18 backbone fine-tuned on expanded tooth crops with focal loss,
Adam optimization, ReduceLROnPlateau scheduling, and early stopping. The saved
training summary records 32 epochs of actual training, best epoch 22, and a
training time of approximately 14.8 minutes. The final best model achieved
strong validation performance with very high normal-class specificity and good
positive-class recall, demonstrating that the overlap-derived labels are
usable for supervised learning despite the sparsity of the expert masks.

The engineering lesson from this module is that careful dataset construction
contributed more to final performance than architectural novelty. The backbone
is a standard ResNet18; the performance gain comes from fixing annotation bugs,
using anatomically correct expanded crops, and correcting the severe class
imbalance before optimization.

\section{Module 5: \textit{Bone Loss Severity Classification}}
\label{sec:impl-module5}

Severity estimation is implemented as a second stage that only receives crops
already considered positive for bone loss. In the primary version used in this
report, the target labels are derived from the overlap ratio itself:
mild, moderate, and severe. A separate three-class ResNet18 is trained on these
positive crops using focal loss. The best result occurs at epoch 2 with a
macro-F1 of 0.7208, which is acceptable for a first severity baseline but also
shows that the available data volume is limited.

This module is clinically relevant because a binary disease flag is not
sufficient for treatment planning. However, it is still fundamentally tied to
the overlap-label construction strategy, meaning its clinical interpretation is
only as good as the quality of the mask-to-tooth mapping.

\section{Module 6: \textit{CEJ-based Bone Loss Estimation}}
\label{sec:impl-module6}

The CEJ-based branch was implemented as an exploratory module because CEJ to
bone-crest distance is closer to the clinical gold standard for periodontal
assessment than a purely mask-derived severity label. The improved v2 pipeline
uses CLAHE preprocessing, column-wise CEJ and apex detection, a focused search
window for the bone crest, interquartile-range outlier removal, and a confidence
scoring mechanism. On 296 analyzed crops, the module reported 100\% successful
landmark extraction, but only 62.5\% of the estimates were marked reliable by
its own confidence criterion.

The more important finding is not the raw detection rate but the limited
agreement with the overlap-based severity labels: 15.1\% exact agreement and
61.6\% agreement within \(\pm 1\) severity class. This indicates that the CEJ
heuristic is still too unstable to replace the overlap-based severity branch as
the primary reporting method on panoramic OPGs. The module is nevertheless
worth retaining because it exposes the exact clinical difficulty of OPG-based
bone-level estimation and gives a concrete path for future improvement using
better landmark models or higher-resolution radiographs.

\section{Integration and Pipeline Orchestration}
\label{sec:impl-integration}

At the architecture level, the pipeline is meant to be orchestrated by a single
controller script that accepts one OPG and returns a tooth-wise report.
However, that final orchestration layer is not yet implemented in the checked
repository. The current command-line scripts for \texttt{build\_dataset.py},
\texttt{train\_model.py}, and \texttt{run\_inference.py} are placeholders. In other words, the
building blocks exist, but the project has not yet crossed the final step from
independent modules to one executable clinical workflow.

This distinction matters for the report. It would be inaccurate to claim that
the system currently accepts a full OPG and produces the final JSON report
automatically. What is accurate is that the disease-analysis modules and their
supporting preprocessing code are already in place, and the repository is now
at the stage where the major remaining work is integration: YOLO tooth
detection, FDI-aware indexing, cross-stage validation, and final report assembly.
