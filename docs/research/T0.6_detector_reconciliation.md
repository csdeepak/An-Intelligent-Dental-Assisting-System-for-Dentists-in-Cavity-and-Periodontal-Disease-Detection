So the two runs differ on exactly four axes — image size, batch, patience/workers (tied to
resolution's memory footprint), and rotation augmentation — everything else, including the
dataset version and split, is held constant. That narrows what the ~16-point val mAP@0.5 gap
can be attributed to: primarily resolution (independently supported by Mutlu et al. 2026,
cited below), with rotation augmentation as a secondary, unisolated factor — the two were
never varied independently, so this comparison cannot separate their individual contributions.
That ambiguity doesn't change the decision below (A100 wins outright on the metric that
matters), but it does mean this pair of runs cannot itself be cited as an augmentation
ablation.

**Decision: the A100 run's configuration (imgsz 1024, batch 32, patience 30, workers 8,
degrees 10, seed 42/deterministic, all other args exactly as recorded in
`models/06_yolo_detection_a100_run/train_args.yaml`) is the canonical base config going
forward.** This is a data-justified call, not a coin flip: the A100 run wins by ~16
mAP@0.5 points on validation alone, before the H200 run's total lack of test-set evaluation
is even considered. `docs/research/MASTER_PLAN_2026H2.md` §3 R1 independently supports 1024px
over 768px (Mutlu et al. 2026 resolution finding, cited there).

**Fixed as part of this reconciliation:** `scripts/yolo/train_yolo.py` had drifted from the
real A100 run (`batch=16` in the script vs. the actual `batch=32`, run name `tufts_v1` vs.

match `train_args.yaml` exactly, args-for-args, so the script is now a faithful

## 2. Pre-registered acceptance criterion for the YOLOv11l-seg retrain (R1)

Declared **before** the segmentation retrain is run, per T0.6's explicit instruction not to
pick a criterion after seeing results. Once the retrain starts, this section does not change
— if the result disappoints, that is reported honestly (as a new `RESULTS_LOG.md` entry), not
used as a reason to retroactively loosen the bar here.

**Training config:** identical to §1's canonical base (imgsz 1024, batch 32, patience 30,
workers 8, optimizer AdamW, lr0 0.001, degrees 10, seed 42, all clinical-augmentation choices
unchanged), with only two deliberate changes: `model=yolo11l-seg.pt` in place of `yolo11l.pt`,
and the dataset format extended to include instance masks (Tufts `teeth_mask`/
`teeth_polygon.json`, converted to YOLO-seg polygon label format). Same frozen 70/15/15
Tufts split — no re-splitting.

**Test set discipline:** the held-out test split is touched exactly once, for final reporting,
after the checkpoint is already selected on validation. No threshold tuning, no checkpoint
cherry-picking, and no architecture changes based on test-set performance — same rule already
in force for Ningxia (`MASTER_PLAN_2026H2.md` §4.2).

**Acceptance bar — the new segmentation model replaces the frozen bbox model (§1) as the
pipeline's canonical Stage-1 detector only if, on the held-out test split:**

1. **Box mAP@0.5 ≥ 0.75** — no worse than 0.03 absolute below the existing bbox model's
   0.7824, allowing for the small trade-off a seg head sometimes costs on pure box accuracy.
2. **Mask mAP@0.5 ≥ 0.65** — no prior mask baseline exists on this data to compare against
   (segmentation is greenfield here, see §3), so this floor is a judgment call: a mask must
   at minimum give a materially usable instance signal for R2's mask-aware cropping and FDI
   assignment on sparse arches, not just marginally beat "no mask at all."
3. Both numbers reported with the same rigor as the existing bbox entry — precision, recall,
   both split sizes, instance counts — as a new dated `RESULTS_LOG.md` entry, never
   overwriting the 2026-04-23 bbox entry.

**If either bar is missed:** report the result honestly, keep the current bbox model as
canonical, and treat R1/R2 as a documented negative or partial result rather than silently
lowering the bar to declare success. This mirrors how R7 (CEJ keypoint head) was already
handled — a clean documented "no" is an acceptable outcome in this project.

**If both bars are met:** the seg model becomes canonical Stage-1, `docs/results/model_metrics.md`
and `docs/results/PAPER_MATERIAL.md` are updated per `CLAUDE.md` rule 1, and R2 (mask-aware
cropping) proceeds against its masks.

## 3. Why the retrain is blocked right now

`docs/research/MASTER_PLAN_2026H2.md` §3 R1 states Tufts "already ships `Segmentation/Segmentation/teeth_mask`
and `teeth_polygon.json` ... no new annotation is required." **Neither file is present on
this machine as of 19 Aug 2026** — `data/tufts/ZIP/Segmentation/Segmentation/` currently
contains only `teeth_bbox.json`, despite both being referenced in `.gitignore` and in
`configs/dataset_config.yaml`'s path declarations.

**Correction, found while inspecting the archived EDA notebook
(`notebooks/bone_loss/01_tufts_data_exploration_v2.ipynb`, cell 6/7 output, from when these
files were last actually on a Drive mount) — the two annotation sources are not
interchangeable:**

- **`teeth_mask/` (raster masks) is incomplete at the source** — the notebook's own
  existence-check output records **308 files for 1,000 images**. This is not a "no new
  annotation required" asset; two-thirds of it doesn't exist.
- **`teeth_polygon.json` is complete** — 1,000 JSON records, one per image, same
  `External ID` key scheme as `teeth_bbox.json`. This is the usable segmentation source, and
  the master plan's claim holds for *this* file specifically. Confirmed schema (per object,
  inside `Label.objects[]`): `title` (tooth number, matches `teeth_bbox.json`), `bounding box`,
  and `polygons` — a **list of point-lists**, not a single polygon. In the one record inspected,
  most objects carry one large primary contour (tens of points) plus several 1–4 point
  fragments that look like edge-tracing noise, not real disjoint mask regions. The converter
  written in §4 below picks the largest-area polygon per object and drops the rest; this
  heuristic is unverified beyond the single record read here and **must be visually spot-checked
  against a handful of real OPGs once the file is back on disk**, before trusting it for a
  training run.

**Ningxia** does ship its own complete segmentation masks (confirmed present in
`data/ningxia/manifest.csv`) and remains a fallback if Tufts `teeth_polygon.json` cannot be
recovered — but Tufts is the training-split dataset here; Ningxia is reserved as the
untouched external test set (§4.2), so training a detector on it would break that separation.

**Before the seg retrain can start:** re-fetch/locate `teeth_polygon.json` (not `teeth_mask/`)
from the original Tufts source and verify it covers the same 1,000-image set as the frozen
split. **Still not found, checked again 20 Aug 2026** after `_repo_archive/yolo_a100_run_workspace/`
and `_repo_archive/datasets_workspace/` were populated on this machine from a separate
session (see §1's freeze above) — `datasets_workspace/` turned out to contain only the small
scripts and notebooks (`convert_tufts_to_yolo.py`, `evaluate_yolo.py`, `train_yolo.py`,
three `.ipynb` files, 22 MB total), not the 2.2 GB of raw Tufts data the original
`ARCHIVE_MANIFEST.md` describes it as having held (`Radiographs/`, `Radiographs_rotated/`,
`Segmentation/`, etc.) — none of that came across. No raw Tufts source images exist on this
machine either, which independently blocks crop re-derivation from the now-frozen detector
(§1), not just the seg retrain. Flagged for the user, who has access to the original
download source (most likely Google Drive, per `MASTER_PLAN_2026H2.md` §4.4 and the Colab
mount path in `notebooks/bone_loss/01_tufts_data_exploration_v2.ipynb`).

## 4. What's ready now

`scripts/yolo/convert_tufts_to_yolo_seg.py` (polygon JSON → YOLO-seg label format) and
`scripts/yolo/train_yolo_seg.py` (training script, config matches §2 exactly) are both
prepared so that once `teeth_polygon.json` lands, the retrain can start immediately without
further engineering delay. **Both are untested** — no GPU available in this environment, and
no polygon data to test the converter against — so treat them as reviewed drafts, not
verified scripts, until they have actually run once. The largest-polygon-per-object heuristic
in the converter (see above) is the single biggest correctness risk in this pair of scripts
and should be the first thing checked once real data is available.
