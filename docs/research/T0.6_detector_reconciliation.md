## 2. Pre-registered acceptance criterion for the YOLOv11l-seg retrain (R1)

Declared **before** the segmentation retrain is run, per T0.6's explicit instruction not to
pick a criterion after seeing results. Once the retrain starts, this section does not change
— if the result disappoints, that is reported honestly (as a new `RESULTS_LOG.md` entry), not
used as a reason to retroactively loosen the bar here.

**Training config:** identical to §1's canonical base (imgsz 1024, batch 32, patience 30,
workers 8, optimizer AdamW, lr0 0.001, degrees 10, seed 42, all clinical-augmentation choices
unchanged), with only two deliberate changes: `model=yolo11l-seg.pt` in place of `yolo11l.pt`,
and the dataset format extended to include instance masks (Tufts `teeth_mask`/
`teeth_polygon.json`, converted to YOLO-seg polygon label format). Same frozen 70/15/15
Tufts split — no re-splitting.

**Test set discipline:** the held-out test split is touched exactly once, for final reporting,
after the checkpoint is already selected on validation. No threshold tuning, no checkpoint
cherry-picking, and no architecture changes based on test-set performance — same rule already
in force for Ningxia (`MASTER_PLAN_2026H2.md` §4.2).

**Acceptance bar — the new segmentation model replaces the frozen bbox model (§1) as the
pipeline's canonical Stage-1 detector only if, on the held-out test split:**

1. **Box mAP@0.5 ≥ 0.75** — no worse than 0.03 absolute below the existing bbox model's
   0.7824, allowing for the small trade-off a seg head sometimes costs on pure box accuracy.
   **Caveat added 21 Aug 2026, before the run (§3.5):** the seg test ground truth holds 3,930
   instances against the bbox test set's 3,924 — 6 real teeth that the bbox converter dropped
   on a corrupt `bounding box` field. Same images, same split, 0.15% more instances. So this
   comparison is near-like-for-like, not exactly like-for-like. This is stated here rather
   than discovered afterwards; the 0.75 bar is **not** being adjusted for it.
2. **Mask mAP@0.5 ≥ 0.65** — no prior mask baseline exists on this data to compare against
   (segmentation is greenfield here, see §3), so this floor is a judgment call: a mask must
   at minimum give a materially usable instance signal for R2's mask-aware cropping and FDI
   assignment on sparse arches, not just marginally beat "no mask at all."
3. Both numbers reported with the same rigor as the existing bbox entry — precision, recall,
   both split sizes, instance counts — as a new dated `RESULTS_LOG.md` entry, never
   overwriting the 2026-04-23 bbox entry.

**If either bar is missed:** report the result honestly, keep the current bbox model as
canonical, and treat R1/R2 as a documented negative or partial result rather than silently
lowering the bar to declare success. This mirrors how R7 (CEJ keypoint head) was already
handled — a clean documented "no" is an acceptable outcome in this project.

**If both bars are met:** the seg model becomes canonical Stage-1, `docs/results/model_metrics.md`
and `docs/results/PAPER_MATERIAL.md` are updated per `CLAUDE.md` rule 1, and R2 (mask-aware
cropping) proceeds against its masks.

### 3.2 A second undocumented gap found and closed: rotation direction

The raw `Radiographs/Radiographs/` images are **landscape, 1615×840** — not portrait
840×1615, which every script in this repo (`convert_tufts_to_yolo.py`,
`convert_tufts_to_yolo_seg.py`) assumes `Radiographs_rotated/` already is. That rotation step
existed at some point (hence the folder name every script expects) but was never itself
captured as code anywhere in this repo or its archive — it had quietly become tribal
knowledge, then just missing knowledge, exactly the failure mode this whole document exists
to prevent.

**Rotation direction was not assumed — it was derived empirically and checked twice:**

1. Rotated a sample image (`1.jpg`) both 90° clockwise and 90° counter-clockwise, cropped
   both at several real tooth bounding boxes from the already-committed `teeth_bbox.json`,
   and visually compared. Clockwise produced coherent tooth anatomy (crown + tapering root,
   consistent radiopaque structure); counter-clockwise produced an incoherent floating blob
   at the same coordinates.
2. Confirmed far more thoroughly using `teeth_polygon.json`: overlaid the converted polygons
   (via the largest-fragment heuristic below) on 7 different clockwise-rotated radiographs
   (both hand-picked and randomly sampled from a real end-to-end conversion run, §3.4) and
   visually checked every polygon. All of them trace real tooth outlines precisely — crowns,
   roots, both dental arches where visible in frame. No ambiguity.

Formalized as `scripts/yolo/rotate_tufts_radiographs.py` (new), which documents this finding
in its own docstring and asserts the expected raw (1615×840) and rotated (840×1615)
dimensions rather than silently trusting the transform on a future run.

### 3.5 The real `dataset_seg/` was built — and doing so exposed a defect in the *bbox* dataset

With the frozen split recovered (§3.3), `scripts/yolo/convert_tufts_to_yolo_seg.py` was run
against the real inputs — the real frozen split, all 1,000 rotated radiographs, the real
`teeth_polygon.json`. Not a rehearsal this time: the output is the actual training input for
R1, at `data/tufts/dataset_seg/` (gitignored, `.gitignore:94`).

| Split | Images | Label files | Instances | Empty labels |
|---|---|---|---|---|
| train | 700 | 700 | 18,268 | 21 |
| val | 150 | 150 | 3,807 | 5 |
| test | 150 | 150 | 3,930 | 6 |
| **total** | **1,000** | **1,000** | **26,005** | **32** |

The script was **not** copy-patched to run this time. Its path constants were made
environment-overridable (`TUFTS_ROOT`, `TUFTS_IMG_DIR`, `TUFTS_POLY_JSON`, `TUFTS_SPLIT_CSV`,
`TUFTS_SEG_DATASET_DIR`), defaulting to exactly the previous hard-coded values. The 20 Aug
verification run had to patch a throwaway copy, which means the thing that ran was not the
thing under review; that is now fixed, and the same env vars are what will point the script
at the data on the GPU box.

**The finding.** Comparing the new seg labels against the bbox labels of the *same images on
the same frozen split*, per image: 942 of 1,000 images match instance-for-instance, and the
other 58 have **1–3 more** seg instances than bbox. Never fewer. The gap is exactly 66
objects, and it is fully explained:

- `teeth_polygon.json` and `teeth_bbox.json` carry **identical object lists** for every one of
  the 1,000 images — verified, zero images differ in object count.
- `convert_tufts_to_yolo.py` (the bbox converter) drops any object whose `bounding box` field
  is under 2 px wide or tall, as "degenerate". That filter fires on exactly **66** objects.
- For those same 66 objects the **polygon is intact and large**: 1,617–13,425 px² in area,
  142–682 points, extents up to 167×223 px. Their `bounding box` fields read `(1, 1)` or
  `(1, 2)`.
- Their `title` values are ordinary Universal tooth numbers spread across the arch (25, 24,
  22, 6, 11, …, plus primary-tooth letters B/C/I/J/L) — not a distinct annotation class.
- Three were rendered with their polygons overlaid on the radiograph and inspected: real
  tooth-sized radiopaque structures, in plausible arch positions, not slivers or noise.

**So the corrupt field is the bounding box, not the annotation.** These are 66 real,
fully-annotated teeth that the existing bbox dataset silently discarded — meaning the frozen
detector was trained on a training set missing 47 teeth and evaluated against val/test ground
truth missing 13 and 6 teeth respectively. In test terms that is 6 of 3,930, **0.15%** of
instances: far too small to move mAP@0.5 = 0.7824 meaningfully, but a real data-quality bug
in the published-facing baseline, and one that is only visible because both datasets now sit
on the same split.

**Decision: keep all 66 in the seg dataset; do not replicate the bbox converter's filter.**
Dropping valid annotations to match a known bug would be propagating the bug for cosmetic
comparability. The cost is that the seg and bbox test sets are not byte-identical ground
truth — recorded as a caveat in §2 rather than silently absorbed. `convert_tufts_to_yolo.py`
was deliberately **not** changed: touching it would invalidate the frozen detector's
reproducibility, which §1 exists to protect. It carries a comment pointing here instead.

## 4. What's ready now

**As of 21 August 2026 the seg retrain has no remaining data blockers.** Every input exists,
on this machine, verified: the frozen split (§3.3), the rotated radiographs, the polygon
annotations, and the built `data/tufts/dataset_seg/` itself (§3.5). `train_yolo_seg.py` is
still the one genuinely unrun piece — no GPU has been available in any environment this has
been prepared in.

**What a GPU environment needs to actually execute the real training run, in order:**

1. `teeth_polygon.json` and the raw `Radiographs/` — available (Google Drive link in §3.1;
   also present locally at `data/tufts/ZIP/...` and
   `_repo_archive/datasets_workspace/Radiographs/`). This repo does not and should not commit
   390 MB of data.
2. Run `rotate_tufts_radiographs.py` to produce `Radiographs_rotated/` — **already done on
   this machine**, `_repo_archive/datasets_workspace/Radiographs_rotated/`, 1,000 files
   verified portrait 840×1615.
3. `outputs/eda_tufts/split_v1.csv` — **found and verified** (§3.3), at
   `_repo_archive/datasets_workspace/outputs/eda_tufts/split_v1.csv`. Nothing to substitute,
   nothing to decide.
4. Run `convert_tufts_to_yolo_seg.py` to build `dataset_seg/` — **already done** (§3.5),
   `data/tufts/dataset_seg/`, 26,005 instances. Rebuildable anywhere with:

   ```bash
   TUFTS_ROOT=<datasets_root> \
   TUFTS_IMG_DIR=<datasets_root>/Radiographs_rotated \
   TUFTS_POLY_JSON=<datasets_root>/Segmentation/teeth_polygon.json \
   TUFTS_SPLIT_CSV=<path>/outputs/eda_tufts/split_v1.csv \
   TUFTS_SEG_DATASET_DIR=<out>/dataset_seg \
   python scripts/yolo/convert_tufts_to_yolo_seg.py
   ```

5. Copy `data/tufts/dataset_seg/` (or rebuild it per step 4) onto the GPU box, fix
   `data.yaml`'s absolute `path:` for that machine, and run `train_yolo_seg.py` against the
   pre-registered criterion in §2.
